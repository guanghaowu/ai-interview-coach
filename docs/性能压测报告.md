# 项目 A 性能压测报告

> 测试日期：2026-09-27 ｜ 被测版本：`main` 分支
> 复现命令：`bash bench/run-bench.sh`（需 `docker compose up -d` 且 `ai-coach-app` healthy）

---

## 一、为什么做这个

在此之前，项目里**一个性能数字都没有**。这带来一个致命问题：

> 面试官问「你说做了 MQ 异步化，那到底提升了多少？」——答不上来。

「我做了异步化」是描述，「异步化把用户等待从 9.3 秒压到 39 毫秒」才是结论。
本报告的唯一目的就是把前者变成后者，并且**所有数字都可复现**。

---

## 二、测试环境与方法

### 环境

| 项 | 值 |
|---|---|
| 部署方式 | Docker Compose 单机（6 容器：mysql / redis / rocketmq-namesrv / rocketmq-broker / app / web） |
| 宿主 | Windows，Docker Desktop（Linux 容器） |
| 压测客户端 | 与服务端**同机**（Node 内置 `http`，见下） |
| 数据库连接池 | Druid `initial-size=5, min-idle=5, max-active=20` |

> ⚠ 局限：单机 Docker、客户端与服务端同机，**网络开销被严重低估**（基线 p50 仅 25ms）。
> 这些数字用于**横向对比与量级判断**，不等于生产容量规划。

### 压测工具：为什么自己写

本机没有任何压测工具（wrk / ab / JMeter / autocannon / hey 全部缺失）。更重要的是，
**通用工具只看 HTTP 状态码，而本项目的业务错误是「HTTP 200 + `body.code != 0`」**
—— 限流被拒时 HTTP 仍是 200，通用工具会把被限流的请求全部计为「成功」，结论完全相反。

所以用 Node 内置 `http` 模块写了零依赖压测器 `bench/bench.js`（约 190 行），
特性：解析 `body.code` 分别统计 HTTP 状态码与业务码、keep-alive 连接复用、
输出 P50/P90/P95/P99、支持预热、支持 `--json` 输出。

### 两个必须记录的环境坑

| 坑 | 现象 | 原因与解法 |
|---|---|---|
| **Git Bash 改写命令行参数** | 所有请求返回 **400 Bad Request** | MSYS 会把「以 `/` 开头的参数」改写成 Windows 路径：`--path /api/health` → `--path C:/Program Files/Git/api/health`。解法：`export MSYS_NO_PATHCONV=1`（`run-bench.sh` 已内置；`bench.js` 也加了防御性报错） |
| **`grep` 把中文输出判为二进制** | 查询结果打印 `Binary file (standard input) matches` | mysql 客户端输出的中文表格含特定字节序列，grep 误判。解法：去掉 grep 或加 `-a` |

## 三、测试结果

### 3.1 接口吞吐与延迟（并发 50）

| 场景 | 请求数 | 耗时 | **QPS** | p50 | p90 | **p99** | max |
|---|---|---|---|---|---|---|---|
| `GET /api/health`（基线，无 DB） | 3000 | 1562ms | **1920.6** | 25.0ms | 30.2ms | 41.9ms | 64.9ms |
| `GET /sessions`（列表，分页+计数） | 2000 | 6175ms | **323.9** | 147.1ms | 232.2ms | **336.8ms** | 418.5ms |
| `GET /sessions/{id}`（详情，多表聚合） | 1000 | 1958ms | **510.7** | 92.9ms | 145.3ms | 211.6ms | 276.7ms |
| `POST /create`（提交，并发 30） | 30 | 235ms | 127.6 | 99.7ms | 221.4ms | 226.2ms | 226.2ms |

**读法**：基线 QPS 1920 → 列表接口 324，说明**瓶颈在 DB 路径**（约 6 倍衰减）。
列表接口 p99 337ms 是全站最大延迟来源。

### 3.2 异步化收益：用户等待时间 9.3 秒 → 39 毫秒

这是本项目最核心的一组数字。

**「同步模型下用户要等多久」** = AI 调用的真实耗时（来自 `ai_call_log.duration_ms` 埋点）：

| 样本 | 耗时 |
|---|---|
| sessionId=42（AgentLoop 1 轮，5 题） | 8300ms |
| sessionId=41（AgentLoop 1 轮，5 题） | 10375ms |
| **平均** | **9338ms（约 9.3 秒）** |

**「异步化后提交延迟」** = 冷路径实测（每次用不同 JD，必然未命中缓存 → 真实走 MQ 投递）：

| 第 N 次 | 1 | 2 | 3 | 4 | 5 | 均值 |
|---|---|---|---|---|---|---|
| 提交延迟 | 37.6ms | 42.1ms | 38.3ms | 37.3ms | 39.4ms | **约 39ms** |

> **结论：异步化把「创建面试会话」的用户等待从 9.3 秒降到 39 毫秒，约 240 倍。**
>
> 机制：主链路只做「建会话 + 投 MQ 消息」；AI 出题在 `InterviewConsumer` 中异步执行，
> 前端通过轮询 `GET /api/interview/{id}` 获取结果（`status` 0=出题中 / 1=完成 / 2=失败）。

### 3.3 限流有效性：拦截率 70%

`POST /create` 并发 30 次（令牌桶容量 10/天）：

| 结果 | 次数 | 占比 |
|---|---|---|
| 通过（`code=0`） | 9 | 30% |
| **被限流拒绝（`code=429`）** | **21** | **70%** |

- 该账号在预热阶段已消耗 1 次配额，故通过 9 次（而非 10 次）——**令牌桶计数精确**
- 被拒响应体：`{"code":429,"message":"请求过于频繁，请稍后再试"}`
- Redis 中对应 key：`rate:interview:user:24`
- 限流在**进入业务逻辑之前**由 AOP 切面拦截，被拒请求不产生任何 DB / MQ / AI 开销

### 3.4 幂等去重：9 次重复提交，0 次额外 AI 调用

压测中 9 个通过的请求全部使用**同一个 JD**。结果：

| 指标 | 值 |
|---|---|
| 新建会话数 | 9（sessionId 43-51） |
| 每个会话题目数 | 5（全部正确复制） |
| `agent_rounds` | 0（复用标记） |
| **额外 AI 调用次数** | **0** |

日志佐证：`命中 JD 缓存，复用题目: sessionId=49, 复用 5 道题`（43-51 共 9 条）。

**项目实际存在两层去重，这是本次压测才明确量化出来的：**

1. **同步层（提交时）**——`SessionService` 查 JD 缓存，命中则**同步复制题目并直接返回**，
   请求根本不进 MQ、不调 AI。这是省 Token 的主力。
2. **异步层（消费时）**——`InterviewConsumer.isAlreadyProcessed` 查 `ai_call_log`
   唯一键 `uk_user_md5(user_id, call_md5)`，拦住并发创建与 MQ 重投导致的重复消费。

> 面试话术：**同一份 JD 重复提交 9 次，AI 只调用了 0 次**——因为复用判定放在了提交链路上，
> 而不是等 MQ 消费时才发现重复。省的是真金白银。

## 四、发现的问题与优化项

按投入产出比排序：

### P1. 列表接口是最大瓶颈（p99 336.8ms）

**现象**：基线 QPS 1920 → 列表 324，p99 337ms。

**根因**：Druid `max-active=20`。50 并发下最多 20 个请求持有连接，其余 30 个排队等连接，
延迟被放大。

**方向**（二选一或组合）：
- 给列表/详情加 **Redis 响应缓存**（当前 `@Cacheable` 全项目 0 处使用）。
  读多写少 + 缓存命中不占 DB 连接，对 p99 改善最直接。
- 适度提高连接池 `max-active`（需先确认 MySQL 侧 `max_connections` 与压测机能力）。

### P2. 完全无响应缓存

全项目检索 `@Cacheable` / `@CacheEvict` 结果为 0 处。
当前 Redis 只用于：会话记忆、令牌桶限流、幂等标记。**读接口每次都打 DB。**

### P3. AI 调用耗时缺少多轮统计

当前 `ai_call_log.duration_ms` 只在**出题**链路埋点，且样本量小（AI 调用有成本）。
评分链路（`/answer`）尚未埋点，AgentLoop 的**各阶段耗时**（Planner / Executor / Critic）
也没有拆分记录。补上后可回答「哪一步最慢」。

## 五、复现方式

```bash
# 1. 起全栈
docker compose up -d

# 2. 跑完整压测（会触发至多约 15 次真实 AI 调用，成本约 ¥0.1）
bash bench/run-bench.sh

# 3. 单点压测
export MSYS_NO_PATHCONV=1          # Git Bash 必加，否则全部 400
node bench/bench.js \
  --url http://localhost:8080 \
  --path "/api/interview/sessions?page=1&size=10" \
  --token "$TOKEN" \
  --concurrency 50 --requests 2000 --warmup 100 \
  --label "会话列表"

# 4. 查 AI 真实耗时
docker exec ai-coach-mysql mysql -uroot -p123456 -D ai_coach --table \
  -e "SELECT COUNT(*) n, ROUND(AVG(duration_ms)) avg_ms FROM ai_call_log WHERE duration_ms IS NOT NULL;"
```
